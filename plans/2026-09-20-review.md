# 联系人审核

## 背景

一个陌生人能不能和智能体说上话，现在由 telegram 的 `allowed_sender_ids` 决定：不在名单里的私聊在 channel 层就被拒掉，
连消息都不留；群聊则没有任何门槛，被拉进去就直接聊。名单写在配置里，改一次要改配置、重启节点；飞书与企业微信没有
这一层，谁都能来。

`plans/2026-09-15-bcs.md` 的线框图第 ② 张画了另一种形状：联系人只有待审核与已允许两种，待审核的点进去是审核卡，允许
或拒绝；已允许的可以移除，移除后他下次再联系就重新进待审核。这一支把它做出来，并废掉配置里的名单。

## 目标

- 会话有审核状态。接了 bcs 的节点上，名单外的新会话——私聊也好、群也好——从待审核开始，由 bcs 审；没接 bcs 的
  节点没人审，名单为空就谁来都是已允许，名单不空就名单内已允许、名单外待审核。升级前已有的会话视为已允许，升级后
  老群不会变哑。
- 待审核与已拒绝的会话里的消息只落库：不通知运行时，无论有没有提到智能体，不产生 turn 也不产生 steer。
  `bcc inbox check`、`bcc message check`、`bcc message read` 都看不见这些会话，`bcc message send` 也发不到。
- telegram 的 `allowed_sender_ids` 废除，channel 不再拒绝任何私聊。每个 channel 一个 `allowed_chats` 放行名单：
  列出的会话一建立就是已允许。配置版本不变，`allowed_sender_ids` 就地换名：Telegram 私聊的 chat id 就是对方的
  user id，原来的名单改个键名原样可用。
- 节点有一张配置表，按智能体存键值，这一支只有一个键：待审核与已拒绝的会话的自动回复；空就是黑洞。
- bcs 看得见待审核的会话，能允许、拒绝、移除；节点上行报告审核状态的变化，下行接受审核决定与配置的改动。

## 设计

### 会话的审核状态

`ChannelSession.review: Review`，三个值：`pending`、`approved`、`denied`。节点迁移 `v31_channel_session_review` 给
`channel_sessions` 加 `review TEXT NOT NULL DEFAULT 'pending'`，同一迁移里把已有的行 `UPDATE` 成 `approved`——
升级前的会话是升级前放行过的，不用再审；此后新建的会话由插入语句按下面的规则写状态。

状态怎么变：

- 新建：会话在 provider 那边的 chat id（消息带的 `provider_chat_id`）在所属 channel 实例的 `allowed_chats` 里 → `approved`；否则，节点有人审
  （配了 control，也就是接了 bcs）→ `pending`；没人审时名单为空 → `approved`，名单不空 → `pending`。
- 允许：任何状态 → `approved`。
- 拒绝：任何状态 → `denied`。线框图的「移除」就是拒绝：已允许的会话拒绝后从列表里消失。
- 已拒绝的会话再收到一条入站消息 → 回到 `pending`：这就是「他下次再联系就重新进待审核」。已允许的收到消息状态不变。

状态只在存储里改，改动的入口是命令服务的一个方法 `review_contact(thread_id, decision)`（`decision` 是 `approved` 或
`denied`），它写存储并记一条审计事件 `channel.session.reviewed`（`metadata`：`thread_id`、`review`、`target`、
`target_name`）。这个方法不是 bcc 的命令——审核是操作者的事，不是智能体的。

### 入站的闸

消息照样落库，闸在两处：

- `record_inbound` 里，会话不是 `approved` 时消息写成 `notifies_runtime = 0`。编排器的 ingress 已经按这个标志决定
  通不通知运行时，不用再判一次；未读游标、`notifying_only` 的查询也都跟着这个标志走。审计事件
  `channel.inbound.persisted` 的 `metadata` 多一个 `review`，bcs 由此知道来了一个待审核的联系人。
- 智能体看会话的所有读取——`list_inbox_targets`、`check_messages`、`read_unread_summary`、`list_thread_ids`
  （`threads_in_reach` 用它）、`read_message_history`、`send_message`、`unfollow_thread`——只认 `approved` 的会话。会话被允许后，它在
  待审核期间落下的消息在 `bcc message read` 里读得到，但不算未读、不补发通知；下一条新消息照常触发。

`read_inbox_catalog` 多一个 `review` 参数：默认只列已允许的（bcc 的用法），bcs 的读取按 tab 传 `approved` 或
`pending`，`InboxListResult` 附 `pending_review` 计数，`InboxTargetSummary` 带上 `review`，序列化随之。这是同一个
服务方法多一个参数，与 `pending_only` 一样。

### 放行名单与自动回复

`allowed_chats` 是每个 channel 都认的选项（`[[agent.channel]] allowed_chats = ["…"]`），值是该 channel 里会话的
provider id 的文本形式——Telegram 的 chat id、飞书的 chat id、企业微信的 chat id；私聊在 Telegram 上就是对方的
user id。名单里的会话一建立就是已允许。名单外的看节点有没有人审：配了 control（接了 bcs）就进待审核，由 bcs 定；
没配的节点没人审，名单为空就谁来都允许——不然操作者连自己的 id 都不知道，就再也联系不上智能体了；名单不空才把
名单外的挡在待审核。名单按 channel 实例算：配置里的第 N 个 channel 就是第 N 个实例，消息带着是哪个 bot 收的
（`channel_identity`）和 provider 那边的 chat id（`provider_chat_id`，各 channel 从自己的消息里取），新会话建立时
按此定状态；同 kind 的两个 bot 各有各的名单。`NodeApplication` 把有没有 control 也交给它。接了 bcs 的节点用名单省掉常客的一次审核。

`plugin.py` 不再要求也不再读取 `allowed_sender_ids`；channel 里私聊的名单检查连同 `unauthorized_sender` 的审计事件
一起删掉。配置版本不变（不是结构改动，不值一次升级）：`allowed_sender_ids` 从 telegram 的选项里消失，
`allowed_chats` 是每个 channel 都认的选项；`bcn agent add` 与 README 改说 `allowed_chats`，手里的配置自己改键名。

配置表：节点迁移 v31 同时建 `settings(agent_id TEXT, key TEXT, value TEXT, updated_at_ms INTEGER, PRIMARY KEY
(agent_id, key))`，`IStorage` 两个方法 `get_setting(key)` / `set_setting(key, value)`（按智能体作用域，和其余存储一样）。
这一支只有一个键 `review.reply`：待审核与已拒绝的会话的自动回复正文。这两种会话每收到一条入站消息，若
`review.reply` 非空，节点就用 channel 回这一句（不经 `bcc`，像提醒那样是节点自己的出站）；空就什么也不发。
改这个键走命令服务的 `set_setting`，同样记审计事件 `setting.changed`（`key`，值不记，是文案）。

### 下行与上行

下行请求多两种写：`{"write": "review", "agent_id": …, "thread_id": …, "review": "approved" | "denied"}` 与
`{"write": "setting", "agent_id": …, "key": "review.reply", "value": …}`，与两种读取一样是 pydantic 模型，`answer()`
分别调 `commands.service.review_contact(...)` 与 `set_setting(...)`；`_Read` 改名 `_Request`，`read` / `write` 两个字段区分。
读取多两种：`{"read": "setting", "agent_id", "key"}` 给页面回显；`{"read": "reminders", "agent_id", "actor_id"}`
列该 actor 够得着的、
scheduled 的提醒——后者是命令服务现有的 `list_reminders`。命令服务对外只有一个 `ICommandService`：原来单独的
`IReminderService` 并进来，实现按职责拆成 `orchestration/commands/` 下的几族（messages、reminders、review）在一个
`CommandService` 上组装，`AgentCommands` 与本地的 `CommandDispatcher` 各只持一个 service；方法名跟 `bcc` 的命令走
（`check_inbox`、`check_messages`、`read_messages`、`send_message`、`unfollow_thread`、`schedule_reminder`、
`list_reminders`、`snooze_reminder`、`update_reminder`、`cancel_reminder`），审核族是 `review_contact`、`setting`、
`set_setting`。
`contacts` 读取多 `review` 参数并在应答里附 `pending_review` 计数。响应都是 `{"ok": true, "result": {...}}`。

上行没有新方法：`channel.inbound.persisted` 带 `review`，`channel.session.reviewed` 是新事件；事件文案 catalog 各补
一条（「来了一个待审核的联系人」用不着单独的事件，文案按 `review` 分）。bcs 的联系人栏刷新看的消息事件集合加上
`channel.session.reviewed`，审核完列表跟着变。

### bcs 界面

功能权限点 `agents.approve`。

- 联系人栏标题下面一行两个图标 tab：「会话」（`message-circle`）和「新的联系人」（`user-plus`，右上角 `--accent`
  的红点带待审核数，没有就不显示红点）；选中的 tab 用 `--hi` 平铺底。会话 tab 就是现在的列表，只列已允许的；新的
  联系人 tab 列待审核的，行是头像、名字、「channel · 私聊/群聊 · 首次联系时间」，按首次联系倒序。已拒绝的哪边都不列。
  两个 tab 各是一次 `contacts` 读取带 `review` 参数（节点按状态过滤，分页照旧）；红点的数字来自节点在
  `contacts` 应答里附带的 `pending_review` 计数。
- 新的联系人 tab 里点一行：右栏是审核卡（线框图 ②）：头像、名字、「首次联系」、「<名字> 想和 <智能体> 私聊 /
  想和 <智能体> 群聊」、channel · id · 首条消息时间、首条消息正文，下面「允许」「拒绝」。按钮发
  `POST /agents/<c>/<a>/contacts/<t>/review`，body 是 `review=approved|denied`；处理器下发 `review` 写，成功后允许的
  右栏换成聊天记录并切回会话 tab，拒绝的右栏清空；红点与列表由刷新自己更新。首条消息用现有的 `history` 读取，
  `around` 不给、`limit` 1。
- 聊天栏标题：会话名前面是它的头像，点头像从右侧滑出资料卡（`.drawer`，320px，`--float` 底，覆盖在聊天栏上，
  标题「资料」带关闭）。资料卡自上而下：头像、名字、「channel · 私聊/群聊 · id」；「成员 · n」（节标题前带
  `users` 图标）一个定高 190px 的框，内部滚动，成员是头像网格（34px 头像，名字在下截断，hover 提示全名，一行
  五个）；「定时器 · n」（`alarm-clock` 图标）一个定高 120px 的框，发丝线分隔的行，每行前面是类型
  图标——循环的 `repeat`、一次的 `calendar`——标题一行，下面一行是下一次的时间，循环的前面带周期：
  「每天 · 明天 09:00」，一次的就「明天 14:00」；底部整行
  `--danger` 的「移除群聊 / 移除私聊」，点了先问一句再发 `denied`，成功后关闭资料卡、右栏清空。任务一节这一支不做。
  成员由 bcs 自己从已加载的聊天记录里得来：每条 turn 带着 sender id 与名字，资料卡打开时从当前列出的消息里去重，
  向上翻页或尾巴接上新消息后再算一遍——节点不为 bcs 加 `bcc` 用不到的方法；定时器来自 `{"read": "reminders", "agent_id", "actor_id"}`：
  命令服务的 `list_reminders`，只列 scheduled 的：触发过的和取消的都不列。
- 自动回复的编辑：联系人栏标题右侧一个图标按钮（`message-square-text`），hover 文案「自动回复」，点开一张小卡：
  一个多行输入框、保存；打开时下发 `setting` 读取回显，保存下发 `setting` 写。智能体资料页做出来后挪过去。

智能体读取只认已允许、`read_inbox_catalog` 的 `review` 参数与序列化、`review_contact()` 服务方法与两个审计事件的 metadata。
测试用真实 sqlite 与编排器：陌生人的消息落库但不起 turn，允许后新消息起 turn，拒绝后再来一条回到待审核，
inbox/message 命令看不见未允许的会话。

### Task 2：放行名单与自动回复

测试：名单内的会话一建立就是已允许；接了 bcs 的节点名单外待审核；没接
bcs 的节点名单为空时谁来都允许、不空时名单外待审核；设了回复语的节点对陌生人的每条消息各回一句，没设的一句不回。

重新出现在待审核。

## 验收标准

- 陌生人的消息一条不丢、一个 turn 不起；允许之后一切如常。
- 智能体经 bcc 看不见任何未允许的会话。
- 升级后已有会话与群都是已允许，行为与升级前一致；名单改成 `allowed_chats` 后继续放行同一批人。
- 设了自动回复的节点，陌生人每发一条都收到那一句，仅此而已；没设的一句也没有。
- bcs 上一次允许或拒绝，节点上立刻生效，审计里有 `channel.session.reviewed`。
