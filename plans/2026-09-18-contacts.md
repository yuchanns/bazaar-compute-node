# 下行通道、联系人与聊天记录

## 背景

`plans/2026-09-15-bcs.md` 搭起了 bcs 的框架：节点把审计事件上报给 bcs，bcs 用它们展示电脑与智能体的活动。事件只用来看
活动；任何「现在是什么」——联系人、聊天记录——都要在需要时通过下行通道向电脑下指令实时查。上一计划把下行通道的
协议形状定死（`getUpdates`、`control.result`），把实现留给第一条需要下发的指令。

这一支就是那条指令：智能体模块的中间栏（该智能体的联系人：线程与 DM）和右栏（选中联系人的聊天记录）。

## 目标

- 节点侧：`contrib/server` 在上报之外多一条下行通道，从 bcs 拉取指令，在进程内以本地命令协议执行，结果作为
  `control.result` 事件走同一条上报出口回去。节点仍不开任何入站端口。
- bcs 侧：`getUpdates` 端点、指令表与等待结果的机制、联系人栏、聊天记录栏。电脑离线时这两栏查不到，界面置灰说明。
- 节点的本地命令协议补一条智能体级的指令：列联系人。聊天记录复用已有的 `message.read`。

## 设计

### 协议

沿用上一计划的方法定义，方法都是节点发起的 POST，鉴权与协议版本头不变；`getUpdates` 是新增的方法，协议版本不变。

- `getUpdates`：请求体 `{"offset": <int>}`，`offset` 是节点确认过的最大 `update_id`（首次为 0）。bcs 挂起直到该电脑
  有 `update_id > offset` 的指令，或 25 秒超时；响应 `result = {"updates": [{"update_id": <int>, "request": {...}}]}`，
  超时时 `updates` 为空数组。一次响应最多 20 条，按 `update_id` 升序。
- `request` 是 `NodeApplication._dispatch` 接受的一条请求，原样透传：`{"kind": "command", "resource": ..., "command": ...,
  "agent_id": ..., ...}`。bcs 不理解请求的内容，只负责排队与配对。
- 指令的结果是一条 `control.result` 审计事件：`state = completed`，`correlation.node_id` 为 `agent_id`，`metadata`
  为 `{"update_id": <int>, "response": <_dispatch 的返回值>}`。响应是本地命令协议的信封（`ok` / `result` 或
  `code` / `error`），大小受上报请求上限约束（一批 1 MiB，单条事件不超过一批的一半）；超过的响应由节点截成
  `{"ok": false, "code": "RESULT_TOO_LARGE", "error": ...}` 再上报。
- 确认即偏移：节点下一次 `getUpdates` 带的 `offset` 表示此前的指令都已取走。取走而未回结果（进程重启、执行异常）的
  指令 bcs 不重发——等它的一方超时后按「电脑没有回应」处理。指令没有过期时间以外的状态。

### 节点侧

`ServerAudit`（`contrib/server/audit.py`）已经持有 bcs 地址、token 与会话。下行通道是它的第二个任务：启动后循环
`getUpdates`，对每条指令调用节点交给它的处理函数，把响应作为 `control.result` 事件 `append` 进自己的队列。

处理函数怎么到它手上：core 加一个端口 `IControl`（`core/control.py`），一个方法 `serve(dispatch)`，`dispatch` 的
签名就是 `NodeApplication._dispatch`。`ServerAudit` 同时实现 `IAudit` 与 `IControl`；`NodeApplication.start` 在节点就绪、
首条 health 发出之后，若 `audit` 是 `IControl`，调用 `serve(self._dispatch)`；`stop` 先停下行再停上报。
`logging` 审计不实现它，节点行为不变。

下行循环的规则与上行一致——不阻碍节点：

- 每次 `getUpdates` 用独立的超时（长轮询 25 秒加 5 秒余量）；网络失败、非 200、`unauthorized` 都记进
  `health["control"]`（`last_error`、`last_polled_at_ms`、`served`），退避一个健康间隔后再拉；bcs 不在时循环空转，
  不打日志刷屏。
- 指令逐条执行，同一时刻只执行一条；执行本身走 `_dispatch`，与 bcn.sock 上的请求同一入口、同一校验，命令服务
  自己写的审计（`bcc.message.read` 这类工具事件）照写——一次查看就是一次活动。
- `offset` 只在内存里：进程重启从 0 拉，bcs 会把这台电脑积压的、未确认的指令再给一遍；这些指令的等待方多半已超时，
  节点照常执行并回结果，bcs 收到无人等待的结果只落库。

### 本地命令协议补充

新增一条智能体级指令，不带 `actor_id`：

```
{"kind": "command", "resource": "inbox", "command": "list", "agent_id": "...", "limit": 50, "offset": 0}
```

返回 `IStorageScope.read_inbox_catalog(limit, offset)` 的结果：`targets[]` 每项 `target`（显示形式）、`thread_id`、
`actor_id`、`target_kind`（`dm` / `group`）、`channel`、`pending_count`、`last_activity_at_ms`、`latest_message_id`、
`latest_sender`（`id` / `name` / `display_name`）、`latest_provider_time_ms`、`latest_received_at_ms`，以及
`total`、`shown`、`offset`、`has_more`。`InboxTargetSummary` 多一个 `channel` 字段，从 `channel_sessions.channel`
取，目录查询已经连着这张表；`actor_id` 是 `Actors.for_thread(thread_id).id`——谁替这个会话答话由节点的模式决定
（`session` 下是会话，`dangerous_individual` 下是智能体自己），bcs 不需要知道模式。这条指令不经过会话绑定校验
（它不属于某个会话），`CommandDispatcher` 为它单开一个请求模型，`bcc` 包装器不暴露它。

聊天记录用已有的 `message.read`：`actor_id` 与 `target` 取自联系人那一项，`around_message_id` 与 `limit` 照旧。
它返回的 `messages[]` 已含发言人、方向、时间、正文与附件清单，bcs 直接渲染。

### bcs 侧

存储：新增迁移 `v02_controls`，表 `controls(update_id INTEGER PRIMARY KEY AUTOINCREMENT, computer_id TEXT NOT NULL,
request TEXT NOT NULL, created_at_ms INTEGER NOT NULL, response TEXT, answered_at_ms INTEGER)`，索引
`(computer_id, update_id)`。`update_id` 全局递增，节点的 `offset` 只对自己的电脑有意义。`IStorage` 加四个方法：
`enqueue_control(computer_id, request) -> update_id`、`pending_controls(computer_id, offset, limit)`、
`answer_control(computer_id, update_id, response)`、`control_response(update_id)`；`reportEvents` 收到
`control.result` 时在同一写事务里 `answer_control`。留存清理顺带删掉 `answered_at_ms` 早于窗口的行，
没人回的行按同一窗口删。

等待：进程内一张 `dict[update_id, asyncio.Future]`；`getUpdates` 的长轮询按电脑挂在一个 `asyncio.Condition` 上，
`enqueue_control` 后通知；`answer_control` 后把响应放进对应的 Future。页面请求 `enqueue` 后 `wait_for(future, 10s)`：
超时就是「电脑没有回应」，页面照样返回，指令留在表里。单进程假设与现有 `_owned_agents` 一致。

同一条指令在途时共用一次：`ask(computer_id, request)` 先看进程内的 `_in_flight: dict[(computer_id, 请求 JSON), Future]`
——两个人同时点开同一个智能体、或同一个人的两个标签页同时被通知，只有第一个 `enqueue`，其余等在同一个 Future 上
拿同一份响应；响应到了或超时了这条键就撤掉，下一次再发。键里的请求 JSON 按键排序后序列化，参数相同就是同一条。

端点：`POST /node/getUpdates`，与 `reportEvents` 同一鉴权与信封；挂起期间不占写连接。

页面（都在智能体模块内，都要 `agents.view`，并经 `@sees("computer") / @sees("agent")`）：

- `GET /agents/<computer_id>/<agent_id>`：现有的选中页，右栏改为两栏——联系人与聊天记录。联系人栏是片段
  `GET /agents/<c>/<a>/contacts?offset=`：一次 `inbox.list`，每行头像（按 `target` 名字的 identicon）、名字
  （`target` 的显示形式）、`channel · 群/DM · 相对时间`（`last_activity_at_ms`，用 `clock.py` 现有的文案）、
  未读数（`pending_count` 大于 0 时的小圆标）。按 `last_activity_at_ms` 倒序，50 一页，末尾 `.edge` 同智能体列表的
  滚动翻页（`hx-get="…?offset="`）。电脑离线（`ComputerView.online` 为假）不发指令，栏里一行灰字说明；发了
  没回应也是一行灰字，带「再试一次」。
- 选中一个联系人：`GET /agents/<c>/<a>/contacts/<thread_id>?actor=&target=`，右栏标题是联系人名、channel 与种类，
  内容是片段 `GET …/contacts/<thread_id>/messages?actor=&target=&before=`：一次 `message.read`，`limit` 50，最新的在底部；向上
  滚到顶部的 `.edge` 时带 `before=<最早一条的 message_id>` 再取一页，走 `around_message_id`（只取它之前的那一半，
  多取的丢掉）。消息按发言人连续合并：头像 + 名字 + 时间一行，下面若干文本块；智能体自己的消息名字带 `Agent`
  标签、人带 `Human`；附件只列文件名。不做气泡，不按发言人上色，与 style.html 一致。
- 指令什么时候下发：用户操作时（点开智能体、点开联系人、翻页），以及被通知时——像 epoll，不是定时去拉，也不是
  等用户点刷新。通知来自 bcs 自己收到的事件：节点的入站与出站本来就上报（`channel.inbound.persisted`、
  `channel.outbound.*`）。打开着的栏每 5 秒问 bcs（不是节点）`GET …/contacts?since=<事件 id>`：bcs 先查该智能体
  有没有 `id > since` 的消息事件（一条计数查询），没有就回 204、页面什么都不动；有才下发 `inbox.list` 并回新的栏，
  `since` 换成最新的事件 id。打开着的聊天记录同理：`GET …/messages?since=` 只在该会话有新消息事件时才下发
  `message.read` 拉最新一页并接在底部。没人打开的栏不产生任何指令。
- 智能体列表里的一行只有选中它才拉联系人；离线的智能体仍不可点开。

文案进 `resources/locales`，中英各一份；新的事件文案 catalog 不需要——`control.result` 不在活动卡里显示，
`recent_lines` 已按 catalog 过滤未知事件。

## Tasks

### Task 1：本地命令协议的 `inbox.list`

`InboxTargetSummary.channel`，sqlite 目录查询带出 `channel`；`CommandDispatcher` 新增 `("inbox", "list")` 请求模型与
处理，不需要 `actor_id`，不经会话绑定校验；`MemoryStorage` 同步。测试：真实 sqlite 存储上造两个会话，
`inbox.list` 分页与顺序正确，`bcc` 包装器不暴露它。

### Task 2：下行通道

core `IControl`；`ServerAudit.serve(dispatch)` 的长轮询、逐条执行、`control.result` 上报、健康字段；
`NodeApplication` 就绪后接上，停止时先停下行。bcs 侧 `v02_controls` 迁移、存储四方法、`getUpdates` 端点、
`reportEvents` 里配对 `control.result`、进程内等待、留存清理。测试起真实 bcs：节点拉到指令并回结果；bcs 不在时
节点空转且不阻碍上报；超时无回应的等待方拿到「没有回应」；进程重启后未确认的指令再给一遍。

### Task 3：联系人栏

选中页改三栏；`contacts` 片段、翻页、离线与无回应的说明、`since` 驱动的被动刷新；文案。测试用真实 bcs 与真实节点存储
（`tests/server/_serving.py` 起 bcs，节点侧用 `ServerAudit` 接上一个只有存储与命令服务的最小 dispatch）验证
联系人按活动倒序出现、翻页、离线置灰。

### Task 4：聊天记录栏

`messages` 片段、向上翻页、发言人合并与标签、附件清单、`since` 驱动的追加；文案。测试同上：一段真实对话的历史按顺序渲染，向上翻页
接上更早的一页。

### Task 5：真实运行验证

本机 bcs 与本机节点：在界面上点开一个智能体，看到它的群与 DM，点开一个群看到最近的消息并向上翻一页；停掉节点
后栏里显示离线说明；节点恢复后再点正常。

## 验收标准

- 节点在 bcs 不可达时上报与下行都空转，入站、出站与 turn 不受影响。
- 一条指令恰好执行一次，结果恰好配对一次；等待方超时不影响指令最终落库。
- 联系人栏与聊天记录栏的内容与节点上 `bcc inbox check` / `bcc message read` 看到的一致。
- 离线的电脑点开智能体时两栏是说明文字，不发指令。
